사용 복기 묶음 2: 스크립트·수정 이력 보관 정리

녹음마다 쌓이는 스크립트 파일과 내부 수정 이력의 보관 규칙을 정한다. 대표 결과는 가장 최근 결과로 바꾸고, 보관은 최근 결과 2회분과 사람이 고친 스크립트로 줄이며, 지운 스크립트의 내부 이력은 함께 지우고, 남는 이력은 내용을 바꾸지 않고 압축한다.1

01

방향

재전사와 편집 저장이 쌓아 둔 파일을 녹음 단위로 정리한다. 지우는 것은 스크립트 파일과 그 스크립트의 내부 이력뿐이고, 녹음 원음과 전사 원응답은 그대로 둔다.5

지우는 것 · 남기는 것 · 형식만 바꾸는 것

  • 지우는 것: 녹음마다 최근 결과 2회분 밖의 스크립트 파일(사람이 고친 것 제외), 지운 스크립트의 내부 수정 이력, 지운 스크립트의 AI 교정 시도 기록.
  • 남기는 것: 녹음 원음(Speeches 묶음·내부 사본), 전사 원응답과 실행 기록(Sessions/…/runs), 내부 정규화 revision(Sessions/…/revisions), 사람이 고친 스크립트, 내보낸 Markdown.
  • 형식만 바꾸는 것: 남는 내부 수정 이력. 압축하되 풀면 지금과 바이트가 같다.

원칙

  1. 지우기 전에 알린다. 자동 정리는 재전사 확인창에 정리될 수를 미리 적고, 기존분 정리는 확인창에 수와 용량을 적는다.6
  2. 사람이 고친 스크립트는 자동으로 지우지 않는다.7
  3. 모르면 지우지 않는다. 실행 기록이나 Scripts 목록을 다 읽지 못한 녹음은 건너뛴다.
  4. 압축은 내용을 바꾸지 않는다. 풀어서 원본과 바이트가 같을 때만 원본을 지운다.

02

정책

02-1 대표 결과 (T2a-2)

  1. Scripts 목록의 녹음당 한 행과 Speech 상세의 연결 스크립트는 그 녹음의 스크립트 중 createdAt이 가장 늦은 것이다. 같으면 id가 사전순으로 앞선 것(현행 동률 규칙 그대로).10
  2. 엔진 등급(«결합본 우선»)은 없앤다.
  3. «다른 결과 보기»는 그대로 녹음의 나머지 스크립트 전부다.
  4. 실행 기록을 보지 않는다. 실행 기록이 없는 로컬 재결합 결과도 같은 규칙을 따른다.

실행 기록 기준(«세대의 대표»)으로 고르지 않는 이유: 실행 기록이 없는 로컬 재결합 결과 3개가 빠져, 녹음 DABBD760에서는 9-13 결합본 대신 9-12 pyannote+Whisper 결과가 대표가 된다.11

바뀌는 경우의 예: 결합본을 만든 뒤 Soniox 단독으로 다시 전사하면 Soniox 단독이 대표다. 결합 실행이 화자 분리에서 실패해 Soniox 단독만 새로 남으면 그것이 대표다(현행 안내 «결합 처리 미완료 · Soniox 단독 결과는 Scripts에서 열 수 있습니다.»와 같은 뜻).12

02-2 결과 보관 (T2a-1)

용어

  • 결과: Scripts 폴더의 .dama.json 하나. 스크립트는 실행이 readyForReview가 되었을 때나 로컬 재결합에서만 만들어지므로 결과는 모두 성공본이다. 실패·부분 완료 실행은 결과를 만들지 않는다.13
  • 자식 결과: 실행 기록에 parentRunID가 있는 실행의 결과. 지금은 결합 실행의 Soniox 단독뿐이다(P2·Nemotron 자식은 스크립트를 만들지 않는다).14
  • 세대: 자식이 아닌 결과 하나와, 그 실행의 sonioxRunID가 가리키는 자식 결과. 재사용한 Soniox 결과는 그것을 가리키는 세대 모두에 속한다. 부모 결과가 없는 자식 결과(부모 실패, 부모 스크립트 삭제)와 실행 기록이 없는 결과는 혼자 한 세대다.15
  • 세대 시각: 세대 대표(자식이 아닌 결과, 혼자인 자식은 그 자신)의 createdAt.

규칙

  1. 녹음마다 세대를 시각 내림차순(같으면 대표 id 사전순)으로 세우고 앞 2세대의 결과를 남긴다. 2는 사용자 결정값이다.16
  2. 사람이 고친 결과는 세대와 무관하게 남긴다(아래 판정).
  3. 나머지가 정리 대상이다. 휴지통으로 옮긴다(D-01).

사람 수정 판정

아래 9필드 중 하나라도 비어 있지 않거나, 내장 transcript에 legacy humanEdited Turn 또는 editedText가 있는 단어가 있으면 사람이 고친 결과다. 실측 38개 중 22개.17

  1. turnTexts (문장 수정, 애매한 교정의 사람 선택 포함)
  2. turnNames (화자 이름)
  3. turnSpeakerIDs (등록 인물 연결)
  4. registeredSpeakers (등록 인물)
  5. nameHistory (이름 변경 되돌리기 기록)
  6. deletedParagraphs (발화 삭제)
  7. paragraphBreaks (수동 문단 경계)
  8. paragraphEdits (문단 직접 편집)
  9. reviewRecords (검수 기록)

보호하지 않는 것: 파일 제목(녹음 제목은 인덱스 displayTitle에 있다), showsOriginal(표시 전환), AI 교정만 있는 결과. 마지막은 사용자 자구 «사람이 고친»을 따른 것이며 지금 해당 결과는 0개다(완료 교정 3개는 모두 사람 수정도 있다).

언제 정리하는가

  1. 자식이 아닌 실행이 readyForReview가 되어 그 결과 스크립트를 새로 만든 직후, 그 녹음 하나만.
  2. 설정 «저장 공간 정리…»(§02-5)에서 모든 녹음에 한 번.

자식 결과 저장(«Soniox 단독» 중간 저장), 이미 있는 스크립트를 다시 연 경우, 앱 시작 때는 정리하지 않는다. 부모 실행이 실패하면 그 시도는 정리를 일으키지 않고, 나중에 재개해 성공할 때 정리한다.

건너뛰는 조건

녹음 전체를 건너뛴다:

  1. 처리 이력을 읽지 못했거나 그 녹음에 이력 문제가 있다.18
  2. Scripts 목록을 읽는 중이거나 Scripts 조회에 파일별 문제(손상·중복 ID·symlink)가 있다.

그 결과만 건너뛴다(다음 정리 때 다시 본다):

  1. 열려 있다(본문 또는 과거 버전 보기) · 저장 중이다.
  2. AI 교정이 실행 중이거나 대기열에 있다.
  3. 목록을 읽은 때와 지금 파일 해시가 다르다(현행 휴지통 이동 검사).

결과 하나를 지우는 순서

  1. 스크립트 파일을 휴지통으로 옮긴다(D-01). 실패하면 아래를 하지 않고 다음 결과로 간다.
  2. 자식 결과였으면 그 실행 ID를 library.savedSourceRuns에 넣는다. 다음 처리 때 다시 만들어지지 않게 하기 위해서다.19
  3. 그 스크립트의 내부 수정 이력 폴더 LibraryRevisions/<스크립트 ID>/를 지운다(D-03 ⓐ). 아직 옮기지 않은 구 배치 파일은 §02-5 정리에서 지운다.
  4. CorrectionAttempts/<스크립트 ID>.json이 있으면 지운다.

결과마다 따로 처리하며 하나의 실패가 다른 결과를 막지 않는다.

알림

  1. 재전사 확인창: 이 실행이 완료됐을 때의 정리 대상 수 N을 미리 센다. 새 세대 = 이 실행 + 재사용할 Soniox 결과(sonioxSourceRunID)로 놓고 규칙을 적용한다. N이 1 이상이면 문구 1을 넣고 문구 2·3으로 기존 «보존» 문장을 바꾼다. N은 상한이다(완료 사이에 사람이 고치면 줄어든다).
  2. 완료: 결과 저장 메시지 뒤에 실제로 지운 수(문구 4)와 못 지운 수(문구 5)를 붙인다.

사례 (테스트 입력)

C는 결합 결과, S는 Soniox 자식 결과, R은 실행 기록 없는 로컬 재결합 결과다. 번호가 클수록 최근이다.

02-3 스크립트 삭제와 내부 이력 (T2a-3)

  1. «Script 삭제…»는 파일을 휴지통으로 옮긴 뒤(현행) §02-2 «결과 하나를 지우는 순서» 2–4를 한다.
  2. 확인창 설명을 문구 6으로 바꾼다. 내부 이력을 못 지우면 완료 메시지를 문구 7로 한다.
  3. 휴지통에서 되돌린 스크립트는 현재 내용(사람 수정 포함)으로 열린다. 지운 AI 버전은 현행 «이 버전을 읽지 못했습니다. 현재 결과는 보존되어 있습니다.»로 실패한다. 이후 저장은 새 이력을 다시 쌓는다.20
  4. «Speech 삭제…»는 바뀌지 않는다.
  5. 앱 밖(Finder)에서 지운 스크립트의 이력은 §02-5 정리에서 지운다.

02-4 수정 이력 압축 (T2a-4)

  1. 형식: raw DEFLATE(RFC 1951). Apple Compression COMPRESSION_ZLIB, Foundation NSData.compressed(using: .zlib). 수준은 Apple 구현의 level 5 하나뿐이다.21
  2. 배치(D-03 ⓐ): LibraryRevisions/<스크립트 ID>/<revisionID>.dama.json.deflate. 두 ID 모두 UUID 검사를 한다.
  3. 쓰기: 지금과 같은 정렬 JSON 바이트를 압축해 덮어쓰기 없이 쓴다. 같은 revisionID 파일이 이미 있으면 풀어서 현행 비교(해독 → 재인코딩 바이트 동일)를 한다. Scripts 폴더의 활성 파일은 압축하지 않는다.22
  4. 읽기(readVersion): 새 배치를 찾고, 없으면 구 배치 LibraryRevisions/<revisionID>.dama.json을 읽는다. 풀 수 없으면 손상이며 현행 오류로 처리한다.
  5. 지문: ScriptVersion.sha256의 뜻을 «압축을 푼 바이트의 SHA256»으로 정한다. 지금 저장된 값은 압축 전 바이트의 SHA256이므로 값이 그대로 맞고 Scripts 파일을 고칠 필요가 없다.23
  6. 저장할 때마다 전체 이력 하나를 쓰는 동작과 개수 상한 없음은 그대로다.

02-5 저장 공간 정리 (설정 · 기존분 1회)

  1. 시작 조건: 변환·AI 교정·녹음 마무리가 진행 중이 아니고, 편집 중이 아니며(canLeave), Scripts 목록을 다 읽었다. 아니면 버튼을 끄고 문구 11을 보인다.
  2. 확인(쓰기 없음): Scripts 조회와 실행 기록으로 보관 규칙의 정리 대상을 고른다. 구 배치 이력 파일을 모두 해독해 소속 스크립트 ID를 얻는다. 현재 Scripts에 없는 ID의 이력은 «지울 이력», 나머지는 «압축할 이력»이다. CorrectionAttempts 중 현재 Scripts에 없는 ID는 «지울 시도 기록»이다. Scripts 조회에 파일별 문제가 있으면 지울 이력과 지울 시도 기록을 0으로 두고 문구 15를 쓴다(읽지 못한 스크립트의 이력을 고아로 오판하지 않기 위해서다).
  3. 확인창: 문구 12–18. 0인 줄은 뺀다. 모두 0이면 확인창 없이 문구 22.
  4. 실행 순서:
    1. 보관 규칙 정리(§02-2, 순서 1–4 포함).
    2. 지울 이력 삭제. 1에서 지운 스크립트의 구 배치 이력도 여기에 든다.
    3. 압축 이전: 파일마다 읽기 → 압축 → 새 배치에 쓰기 → 다시 읽어 풀기 → 원본 바이트와 같으면 원본 삭제. 다르면 새 파일을 지우고 원본을 남기며 실패 1로 센다.
    4. 지울 시도 기록 삭제.
  5. 건별 기록: 내부 저장소 storage-cleanup-log.jsonl에 항목마다 한 줄(시각·종류·스크립트 ID·revisionID·바이트·결과)을 처리 즉시 덧붙인다. 제목·본문은 쓰지 않는다.24
  6. 중단: 앱이 도중에 끝나면 처리 중이던 파일은 원본이 남는다. 다음 정리에서 새 파일과 원본이 함께 있으면 새 파일을 풀어 원본과 대조하고, 같으면 원본만 지운다. 다르면 새 파일을 지우고 다시 압축한다.
  7. 진행 중: 문구 20. 스크립트 편집·저장·변환 시작을 막는다. 녹음은 막지 않는다.
  8. 끝: 문구 21(실패가 있으면 수를 붙인다). 확인 단계가 실패하면 문구 23이며 아무것도 지우지 않는다.

지금 데이터의 예상: 정리할 스크립트 0개, 지울 이력 62개 · 243.1 MB, 압축할 이력 512개 · 9,758.9 MB → 약 651.8 MB, 지울 시도 기록 0개. 앱 안 소요 시간은 안 쟀다(python 해독 62.4초 + 압축·왕복 33.4초).
