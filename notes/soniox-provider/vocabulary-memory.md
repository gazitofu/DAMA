# 반복 용어·인물·회사명 기억 기능 검토

2026-09-11 사용자 요청에 따른 설계 제안. 구현·자동 학습·추가 외부 전송은 아직 하지 않았다. 상태와 후속 범위는 `versions/soniox-provider/plan.md`에서 관리한다.

## 권장 형태

DAMA 안에 **사용자가 확인한 표기 사전**을 로컬로 저장하고, 다음 녹음의 맥락에 맞는 항목을 전사 요청에 넣는다. 이 단계에서는 STT 모델을 재훈련하지 않는다. 사용자가 고친 이름·회사명·용어를 기억하는 기능이며, 음성으로 특정 인물을 알아보는 화자 지문 기능과는 분리한다.

첫 버전은 ‘직접 등록 + 확인한 수정에서 사전 저장 제안 + 녹음별 적용 미리보기’가 적절하다. 반복 출현만으로 자동 확정하면 STT가 반복해서 잘못 인식한 표현을 계속 강화할 수 있다.

## 사용자 흐름

1. 스크립트에서 회사명 등을 고치거나 선택하고 ‘사전에 저장’을 누른다.
2. 표준 표기, 다른 표기/오인식 후보, 종류(용어·인물·회사), 적용 범위(공통·프로젝트)를 확인한다.
3. 녹음 준비 화면에 ‘적용할 사전’과 선택 항목 수를 표시한다. 프로젝트는 사용자가 고르고, 다른 프로젝트 사전은 섞지 않는다.
4. 실제 전송 확인창에서 적용 용어와 제외 용어를 볼 수 있다. 선택된 항목만 공급자에 보낸다.
5. 결과에서 표기가 맞았는지 확인하고 잘못된 사전 항목을 수정·비활성화·삭제할 수 있다. 이미 저장한 원문과 과거 전송 기록은 바꾸지 않는다.

문장 전체 수정에서 무엇이 고유명사인지 확실하지 않으면 후보 위치를 사용자가 지정하게 한다. 다수 수정 문장을 통째로 사전 항목으로 저장하지 않는다. 음성을 확인한 사용자 수정과 단순 AI 제안 수락은 근거 종류를 구분한다.

## 데이터 모델 초안

| 필드 | 의미 |
|---|---|
| id / revision | 이름이 바뀌어도 유지되는 항목 ID와 변경 버전 |
| canonical / aliases | 표준 표기 / 알려진 다른 표기. 전역 자동 치환표로 사용하지 않음 |
| kind | term / person / organization |
| scopeID | 공통 또는 사용자가 선택한 프로젝트 ID. 폴더명이 바뀌어도 유지 |
| description / topic | 짧은 뜻·적용 주제. TR/TRL처럼 비슷한 약어를 구분 |
| personMetadata | 확인된 소속·직함. 음성 임베딩이나 Run의 Speaker A와는 연결하지 않음 |
| state | candidate / confirmed / disabled |
| evidence | 사용자가 지정한 Script/Run/발화 ID, 확인 시점·근거 유형. 원문 전체 복제는 피함 |
| usage | 적용된 서로 다른 녹음 수, 사용자 재확인/거절 이력. 재전사 여러 번을 여러 회의로 세지 않음 |
| timestamps | 생성·최종 확인·변경 시각 |

동명이인은 이름 문자열로 합치지 않고 ID·소속·프로젝트로 구분한다. 회사명 변경도 과거 이름을 삭제하는 대신 기간/별칭으로 기록할 수 있다. 동일 별칭이 여러 표준 표기에 해당하면 자동 선택하지 않고 전송 전 충돌을 표시한다. 참여자 이름을 공통 사전에 저장했다는 이유로 모든 회의에 참석자로 추가하지 않는다.

## 다음 전사에 적용하는 방식

- Soniox: 선택한 항목의 표준 표기를 `context.terms`에 넣는다. 역할·회사 설명은 필요한 것만 짧게 `general`에, 긴 프로젝트 배경은 선택 발췌로 넣는다. 별칭은 표준 표기와 경쟁할 수 있으므로 무조건 모두 terms에 추가하지 않는다.
- pyannote: 현재 검증한 요청 계약에 없는 사전 필드를 만들어 보내지 않는다. 사전은 앱의 검수/별도 AI 교정에 사용할 수 있고, 전사 단계 적용 가능 여부는 공급자 계약을 따로 확인한다.
- 원문 결과를 사전 문자열로 강제 치환하지 않는다. 특히 금액·부정문·TR/TRL처럼 의미가 다른 표현은 원음 검수가 우선이다.
- Run마다 적용 항목 ID/버전과 실제 전송값을 snapshot으로 남긴다. 이후 사전 수정이 과거 요청이나 재개 요청을 바꾸면 안 된다.
- 예산 우선순위는 사용자 필수 선택 → 현재 참석자/프로젝트의 확인된 표기 → 사용자가 선택한 공통 표기 → 참고 발췌다. 기본 맥락이나 필수 선택이 넘치면 조정을 요청하고, 선택 발췌 제외는 미리보기에 명시한다. 임의의 자동 요약·외부 LLM 호출은 기본 동작에 넣지 않는다.

Soniox 공식 문서는 general의 짧은 키/값, 전문 표기의 terms 사용, 문맥 크기 한도를 설명한다. 이것이 사전 저장 기능 자체나 적용 후 정확도를 보장하는 것은 아니다. [공식 Context 문서](https://soniox.com/docs/stt/concepts/context)

## 반복 항목의 후보 수집

두 번째 단계에서 명시적으로 기능을 켠 사용자의 수정 이력과 여러 녹음의 반복 표기를 로컬에서 집계한다. 사용자에게 등록 후보를 제시하되 자동 확정하지 않는다. 빈도가 높다는 이유만으로 신뢰도가 높다고 표시하지 않는다. 초기 후보 임계값은 실제 여러 회의에서 추천 적중률·거절률을 본 뒤 정하며 임의로 품질 수치를 약속하지 않는다.

LLM을 이용한 후보 추출은 필요성이 확인되면 별도 선택 기능으로 추가한다. 그 경우 대상 전사/발췌의 외부 전송이 늘어나므로 원래 전사 동의와 구분해서 알린다. 단순 로컬 사전의 MVP에는 필요하지 않다.

## 보관·삭제·검증

로컬 Application Support 아래 별도 버전 저장소를 둔다. 초기 규모에는 원자적 JSON 저장으로 충분하며 조회·이력 규모가 커질 때 SQLite로 이전한다. 파일은 Git에 넣지 않는다. 활성 사전에서 삭제/비활성화한 항목은 미래 요청에서 제외하고, 사전 변경은 되돌릴 수 있게 한다. 이력까지 지우는 완전 삭제는 별도 범위를 명확히 한다. 과거 Run에는 재현을 위한 전송 snapshot이 남는다는 점을 안내한다.

효과는 동일 음성·같은 모델·동일 문단 표시 정책에서 사전 OFF/ON을 비교한다. 사용자 확인 정답이 있는 이름의 표기 정확도, 틀린 치환·다른 프로젝트 혼입, 반복 확인 부담 감소를 본다. 화자 수 일치나 문장이 자연스럽다는 이유로 성공 처리하지 않는다.

권장 순서: ① 수동 사전·프로젝트 선택·전송 snapshot ② 확인된 수정에서 등록 제안 ③ 여러 녹음의 로컬 반복 후보 ④ 필요 시 화자 지문을 별도 기능으로 검토. 이번에는 ①–④의 구조 검토만 수행했다.
