## 2026-09-13: Soniox + P2 결합 실패의 현재 진단

사용자: UI 모두 확인. Soniox 단독의 텍스트, Pyannote+Whisper의 화자 구분이 가장 좋았으나 Soniox+P2는 미배정으로 과도하게 분절됨. AI 보정 전 결과이며 해결 방안 검토를 요청했다.

이번 범위는 현재 Scripts/저장 원본의 동일 입력 확인 → 미배정 원인 → 실제 읽기 문단 수 → 결합 규칙만 달리한 오프라인 비교다. 이 네 축의 측정으로 진단을 종료한다. 음성 재전송·AI 보정·운영 정규화/계약 변경·새 앱 설치는 범위 밖이다. `work/m0-fixture-review`, HEAD `17694c0`, 다른 소유 dirty7 유지. 기존에 읽은 프로젝트 진입점·규율과 운영 계약을 적용했다.

### 입력과 모델을 먼저 대조한 결과

- 현재 Scripts는 **4개**다. 예전 8개 파일 경로를 재사용하지 않고 현행 목록을 새로 읽었다. 최신 결합본 `BBD7A458…`(Script 파일 `B6760DBF…`), 원 Soniox `F7EE8364…`, 최신 통합 `336E25CC…`, 이전 결합본 `DF6F46D1…`다. 네 파일 모두 AI 교정본/본문 수정본이 없고, 단독/통합 두 파일의 화자 표시이름 수정은 유지했다.
- 현재 분석 WAV의 SHA256을 직접 계산해 네 Run의 provenance와 일치함을 확인했다. 길이 1,313.28초, P2 요청은 모두 `precision-2`, `numSpeakers=3`, `exclusive=true`다. **인원 제약 누락이나 다른 분석 음원이 이번 차이의 원인은 아니다.**
- 최신 결합본의 6,016개 토큰은 원 Soniox와 ID/순서/텍스트/공백/종류/시작·끝 시간이 정확히 같다. 결합 단계가 Soniox 문장을 재작성하지 않았다. Soniox 단독은 감지 화자2, 결합/통합은3이나 인원 일치가 정확도 검증은 아니다.
- 최신 결합본은 이전 Pyannote+Whisper Run `0F20720E…`의 저장 P2 응답을 재사용했다. 이 응답은 `transcription=true`로 생성한 통합 응답이다. 최신 통합 Run `336E25CC…`과 비교하면 **exclusive 502개 구간 전체가 동일**하다. regular는 각각530개이며 일부 시간/신뢰도 값은 달라 완전 동일이라고 주장하지 않는다. 다른 Run의 화자 번호를 사람 신원으로 매핑한 비교가 아니다.

따라서 이번 표본의 큰 차이는 ‘Whisper 쪽은 다른 화자 모델을 사용해서’라고 설명할 수 없다. 두 경로가 같은 단일 화자 시간표를 갖고도 텍스트와 연결하는 방식이 다르다. pyannote 공식 문서도 통합 STT가 별도의 reconciliation을 사용한다고 설명하며, 외부 STT에는 exclusive 시간표와 전사 시간의 겹침량으로 연결하는 예제를 제공한다. [공식 결합 안내](https://docs.pyannote.ai/tutorials/diarization-asr-merge)

### 앱에서 분절을 만드는 두 단계

1. `SonioxPrecisionNormalizer`는 시간 길이가0이면 즉시 null로 만든다. 양수 길이에서도 regular의 다른 화자와 조금이라도 경계가 겹치거나 동시발화가 있으면, exclusive 우세 후보가 있어도 null로 만든다. coverage 0.60 미만도 null이다. 반면 `ManagedNormalizer`는 Pyannote+Whisper가 제공한 단어의 화자를 받아들이고 시간/경계/겹말 경고만 추가한다. 이 비대칭은 저장 응답의 차이와 별개인 앱 정책이다.
2. 결합본은 토큰당 원 Turn을 만들고, `LibraryPresentation.canJoin`은 nil 화자끼리도 합치지 않는다. Soniox는 단어보다 작은 조각과 문장부호도 개별 토큰으로 낸다. 그 결과 미배정657개가 **각각 별도 읽기 문단657개**가 된다. [Soniox 토큰 시간 설명](https://soniox.com/docs/stt/concepts/timestamps)

최신 결합본을 다시 센 값이다. ‘단어’ 대신 **토큰**을 사용한다. lexical도 완성된 단어가 아닌 부분 토큰일 수 있다. 원인은 0길이 → 겹말 → 경계 → coverage/후보 없음 순으로 하나씩 분류했다.

### 저장 응답만 사용한 결합 규칙 비교

같은 최신 결합본을 메모리에서만 변경하고 **실제 DamaCore의 `LibraryScript.validate()`와 `blocks()`**로 검사했다. 텍스트/시간/원 토큰 순서/regular·exclusive/겹말 경고/누락 의심 marker72개를 보존했다. 기존 경고를 재계산하지 않은 원인 분리 실험이며 사용자에게 저장할 완성 후보 Run은 아니다. 모든 비교에서 동률은 미배정, 시간상 교집합이 없으면 가장 가까운 화자로 채우지 않는다.

이 결과는 **배정률과 읽기 분절의 측정**이다. 잘못된 화자 귀속(E1), 짧은 끼어들기 병합(E2), 원문 인식 정확도와 사람의 수정시간은 청취 정답이 없어 미측정이다. 기존 운영 파일에는 어떤 후보도 적용하지 않았다.

### 권고하는 수정 순서

1. **Soniox 원문 + P2 exclusive 연결을 기준으로 재설계.** 겹말/regular 경고는 근거로 보존하되 일괄 미배정 조건에서 분리한다. 공식 예제와 같은 최대 교집합 방식 B를 비교 기준으로 삼고, 경계에서 우세가 약하거나 교집합이 없는 실제 발화는 별도 시간 정렬 대상으로 둔다. 단순 임계값 하향만으로 끝내지 않는다.
2. **말 조각·문장부호를 발화 단위와 구분.** 같은 어절에 속한 부분 토큰을 원문 순서대로 묶어 시간 근거를 평가하고, 문장부호는 연결된 어절/문장의 부호로 취급한다. 시간 원값은 보존하고 파생 정렬 근거를 별도로 기록한다. 같은 어절이라는 이유만으로 화자 경계나 A→짧은 B→A를 넘지 않는다. 근거 없는 lexical은 계속 미배정으로 남기되 부호/조사마다 독립 발화 문단이 생기는 구조를 해소한다.
3. **재사용 응답으로 비교 Run을 만들고 원음을 대조.** 현행/B/어절·부호 보완 후보에서 배정이 바뀐 겹말·경계·0길이·교집합 없음과 짧은 끼어들기 구간을 우선 비교한다. 이미 잘 배정되던 구간도 유지되는지 확인한다. E1/E2와 수정량을 기준으로 승격하고, 적용 시 새 algorithmVersion·새 Run으로 원본/수동 수정본을 보존한다. 이때 새로운 Soniox/P2 호출은 필요하지 않다.

AI 보정은 이 실험의 입력에 넣지 않는다. 현재 결함은 모델 원문 재작성보다 시간 근거와 화자 연결, 토큰과 문단의 관계를 바로잡아야 해결된다. 시간 재정렬만으로 남는 오류가 큰 경우에는 별도 음성 정렬기 또는 저장된 Whisper 전사와의 검증 가능한 정렬을 후속 후보로 검토한다. 문맥만으로 인물 귀속을 추정하지 않는다.

## 제품이 좋아질 방향

목표를 **믿고 쓸 수 있는 화자별 원문까지 드는 비용과 사람의 수정시간**으로 잡는다. 지정 인원이 맞거나 미배정이 줄어도 A의 말을 B에게 붙였다면 개선이 아니다. 같은 녹음에서 E1(잘못된 귀속), E2(여러 화자의 발화 병합), 사람이 고친 구간 수와 소요시간을 함께 비교해야 한다. 정상 요금에는 Soniox 전사, Precision-2 구독/사용량, 재전사 중복, 로컬 처리시간을 포함한다. 현재 Tiro·Clova Note보다 싸거나 정확하다는 비교 결과는 없다.

우선순위는 ① 미배정 원인별 시간 정렬 개선 실험 ② 영구 개인 용어·별칭 프로필 ③ 관련 문서 검색 개선 ④ 충분한 정답 데이터가 쌓인 뒤 Qwen 추가 학습 검토다. ①과 ②는 별도 실험으로 효과를 나눠 측정한다.

| 미배정 | 662 |
| 그중 겹말 | 294 |
| coverage 부족/후보 없음 | 196 |
| 0길이 타임스탬프 | 145 |
| 화자 경계 | 27 |
| 공급자 불일치 경고 | 72 |
| 불일치 경고 중 미배정 | 0 |

따라서 이 표본에서는 단순히 ‘둘이 다르면 P2’라는 규칙만 추가해도 해결할 미배정이 없다. STT 단어의 시간과 화자 구간의 연결을 원인별로 고쳐야 한다.

실제 화자 수 지정은 클러스터 수 제약으로 유용하다. 다만 이것이 모든 단어의 화자 연결을 보장하지는 않는다. pyannote는 일반 겹침 구간과 별도로 한 시점에 한 화자만 있는 exclusive 결과를 제공한다. 이를 STT 정렬에 쓰는 후보를 비교할 수 있다. [공식 화자 수·exclusive 설명](https://docs.pyannote.ai/tutorials/speaker-configuration)

제안하는 첫 실험은 기존 원본 응답을 재사용해 **regular의 겹침 근거를 보존하면서 exclusive를 연결 후보로 사용하는 정책**, 0길이/경계 단어의 시간 정렬 보완을 현행과 비교하는 것이다. exclusive가 실제로 겹친 두 발화의 텍스트를 복원하는 것은 아니다. 원음 청취로 확인할 수 없는 구간까지 가장 가까운 화자로 채우지 않는다. 다른 Run의 같은 번호를 같은 인물로 취급하지 않는다. 승격 기준은 미배정 수 감소와 함께 E1/E2 및 수동 수정시간이 좋아지는지다. 현재 정책을 이 제안으로 전환하지 않았다.

## 참고 폴더가 실제로 사용되는가

**폴더를 지정한 것만으로 항상 사용되지는 않는다.** 현재 앱은 아래 선택에 따라 준비된 발췌를 실제 모델 입력에 넣는다. 이번 구현은 해당 경로를 합성 파일로 검증하고, 소비하지 않는 항목을 Speeches에서 숨겼다. 숨긴 기존 입력은 삭제하지 않는다.

| 처리 | 실제 소비 | 폴더 사용 조건 |
|---|---|---|
| Soniox 단독/운영 결합 | `general`의 맥락·참석자·화자 수 힌트, `terms`의 공통 용어, `text`의 직접 참고·발췌 | 기본 문맥 ON + 폴더 발췌 추가 ON. 기본 폴더 OFF |
| Qwen + P2 | 맥락·참석자·공통 용어·직접 참고·발췌가 로컬 `context`에 들어감 | 참고 폴더 로컬 입력 ON |
| pyannote + Whisper | 실제 화자 수 | 맥락·용어·참고 폴더를 보내지 않음 |
| Scripts의 AI 검수/보정 | 전사와 사람 수정 보호 정보, 기존·추가 참고, 선택 발췌 | 별도 모달의 최종 보정하기. 새 전사 자동 AI는 OFF |

앱의 `ReferenceFolder` → 준비 입력 → `SonioxRequest.context` 및 `QwenRunner` → `qwen_worker.py` → `build_prompt_tokens` 소비 경로를 확인했다. 합성 md 발췌가 Soniox payload builder에 정확히 들어가고, QwenRunner가 시작한 **가짜 worker**가 같은 로컬 컨텍스트를 읽는 테스트도 통과했다. 실제 Qwen 모델이 그 배경 지식을 정확히 따르는지와 한국어 인식 향상은 별도 검증 대상이다.

현재 검색은 UTF-8 md/txt만 읽는다. PDF·Word 파일은 읽지 않는다. 최대300개 경로 탐색, 깊이 제한3, 파일200KB 이하; 문자 그대로의 검색어 매칭으로 파일당 최대3문단(각2,000자), 발췌4,000자, 최대8파일/총12,000자를 고른다. **매칭 점수가0인 내용도 후보로 들어갈 수 있어 의미상 관련성을 보장하지 않는다.** Soniox 최종 입력에는 앱의7,500바이트 예산이 추가 적용된다. 확인창은 실제 포함·제외된 발췌와 전송값을 보여 준다.

Soniox 공식 문서도 조직·주제는 `general`, 인명·브랜드는 `terms`를 권하며, 긴 참고 `text`는 그 둘보다 영향이 약하다고 설명한다. `translation_terms`는 번역용이라 한국어 원문 치환 사전으로 쓰면 안 된다. 공식 컨텍스트 한도와 앱의 보수적 바이트 예산은 서로 다른 기준이다. [공식 context 계약](https://soniox.com/docs/stt/concepts/context)

## KUDOS 같은 개인 지식을 넣는 방법

현재 공통 용어는 **녹음별 입력**이다. 참고 폴더 접근은 기억하지만, 사용자가 자주 쓰는 표현을 학습해 영구 개인 사전으로 승격하거나 가중치를 조절하는 기능은 없다. Qwen에 context를 주는 것은 추론 시 참고이고 모델 가중치의 학습이 아니다.

다음 구현에서는 사용자가 확정한 작은 개인 프로필을 우선 넣는 편이 타당하다. 예를 들면 조직 표준 표기는 `KUDOS`, 알려진 발음/표기 변형은 `큐더스`; 인물은 `이석훈`, 소속은 `KUDOS`, 호칭은 `석훈 상무`로 저장한다. 전사 직전 해당 핵심 용어를 `terms`와 짧은 배경 맥락에 넣고, 문서 발췌는 남는 예산에서 관련된 것만 보충한다. 사용자의 수정에서 별칭 후보를 제안하고 확정된 항목만 누적하면 개선 원인을 설명하고 잘못된 학습을 되돌리기 쉽다.

‘석훈 상무’가 언급되었다고 말한 사람이 이석훈인 것은 아니다. 인명 인식과 화자 신원 연결을 분리해야 한다. 또한 실제 발화에 없는 회사명이나 전체 이름을 원문에 추가해 문장을 확장하지 않는다. 명칭 정규화/배경 정보와 모델 원문은 별도로 보존한다.

용어 프로필 실험은 참고 없음 / 핵심 프로필 / 핵심 프로필+문서 검색을 같은 녹음으로 비교한다. 표준명·별칭 인식률과 함께 잘못된 치환 수, 일반 대화의 품질, 비용·처리시간을 기록한다. 관련 문서 후보는 점수0 제외와 키워드 확장을 먼저 비교하고, 필요할 때 로컬 의미 검색을 검토한다. 모든 문서를 매번 전송하는 방식은 비용과 잡음을 늘릴 수 있다.

Qwen 추가 학습은 별도의 후속 단계다. 공식 학습 예제는 음성 경로와 정답 텍스트 쌍을 사용하며 GPU 학습과 checkpoint 저장/추론을 설명한다. 앱을 많이 쓰거나 참고 폴더를 지정하는 것만으로 이 과정이 실행되지는 않는다. [Qwen3-ASR 공식 fine-tuning 문서](https://github.com/QwenLM/Qwen3-ASR/blob/main/finetuning/README.md)

Mac 전용이라는 기존 조건 안에서 검토하려면, 먼저 이 Mac에서 지원되는 학습 경로와 메모리·시간을 실측하고 인간이 확정한 원문-음성 정답과 평가용 녹음을 분리해야 한다. 현재 로컬 추론 성공을 Mac 추가 학습 가능성의 증거로 대체하지 않는다. 이번 앱에는 자동 학습을 추가하지 않았다.
